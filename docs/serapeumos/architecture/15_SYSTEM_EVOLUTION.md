# MA-15 — System Evolution / Evaluation / Poisoning

**Status:** CLOSED — ARCHITECTURE LOCKED  
**Phase:** Final Master Architecture / Design Gate  
**Implementation:** NOT STARTED

---

## 1. Purpose

MA-15 defines how SerapeumOS may improve itself over time without allowing learning, model output, generated code, telemetry, imported data, or Agent autonomy to silently modify trusted system behavior.

It governs:

- System Evolution Truth;
- learning and candidate generation;
- evaluation;
- experimentation;
- comparison against baselines;
- poisoning/contamination defenses;
- promotion;
- rollback/supersession;
- evolution authority;
- autonomous-improvement boundaries.

MA-15 does not define the detailed product UI, software update mechanism, signing/SBOM implementation, or release-test thresholds. Those belong to MA-16, MA-18, MA-19, and MA-20.

---

## 2. Governing principle

### LOCKED

> **SerapeumOS may learn automatically, test automatically, and propose improvements automatically. It may change trusted production behavior only through an explicitly governed promotion path appropriate to the change class.**

No:

- model;
- Agent;
- lesson;
- Dreaming output;
- generated code;
- benchmark score;
- telemetry pattern;
- external research result

is itself promotion authority.

---

## 3. System Evolution Truth

### LOCKED

System Evolution Truth is its own durable state domain.

It contains records such as:

- observed problems/opportunities;
- candidate improvements;
- candidate versions;
- evaluation plans;
- evaluation evidence;
- baseline comparisons;
- risk classification;
- reviewer decisions;
- approval decisions;
- promotion state;
- rollback/supersession history;
- post-promotion monitoring outcomes.

### LOCKED

System Evolution Truth is distinct from:

- Organizational Truth;
- Execution Truth;
- Epistemic Truth;
- Working Context.

An evaluation result may reference those domains but does not replace their authority.

## 4. Existing Ankole learning substrate

### REPOSITORY FACT

Ankole already includes `Brain.Dreaming`, which runs ordered maintenance phases including:

- consolidation;
- patterns;
- link/timeline extraction;
- emotional weighting;
- take grading/calibration;
- contradiction discovery;
- schema suggestions;
- merge suggestions;
- purge;
- skill lessons.

A failing phase is isolated and reported rather than silently blocking all other phases.

### REPOSITORY FACT

Ankole `Brain.SkillLessons`:

- derives candidate field notes from accumulated evidence;
- uses failed calls and human mid-run corrections as evidence sources;
- instructs the reflection process to treat tool/error output as untrusted data rather than instructions;
- requires transferable evidence rather than manufacturing lessons;
- applies proposed lessons through trusted Library gates;
- reviews lessons for renewal, obsolescence, or lapse.

### LOCKED

These mechanisms are useful **candidate-generation and bounded-learning substrates**.

They are not authority to modify SerapeumOS architecture, security policy, trusted code, or release state.

## 5. Canonical evolution pipeline

### LOCKED

The SerapeumOS System Evolution lifecycle is:

```text
OBSERVE
  ↓
EVALUATE SIGNAL
  ↓
IDENTIFY GAP / OPPORTUNITY
  ↓
PROPOSE CANDIDATE
  ↓
CLASSIFY CHANGE + RISK
  ↓
PROVENANCE / CONTAMINATION / POISONING SCREEN
  ↓
ISOLATED EXPERIMENT
  ↓
COMPARE AGAINST FROZEN BASELINE
  ↓
INDEPENDENT REVIEW WHERE REQUIRED
  ↓
APPROVE / REJECT
  ↓
PROMOTE
  ↓
MONITOR
  ↓
KEEP / ROLLBACK / SUPERSEDE
```

No material stage may be silently skipped merely because the candidate was generated by a high-performing model or Agent.

## 6. Evolution object identity

### LOCKED

Every material evolution candidate has a stable identity and immutable candidate revision.

A candidate revision must be able to resolve to:

- origin;
- proposing Principal/system;
- change class;
- exact candidate content/artifacts;
- provenance;
- affected system scope;
- evaluation plan;
- baseline;
- evaluation evidence;
- approval/review state;
- promotion history.

Changing the candidate materially creates a new candidate revision.

---

## 7. Evolution lifecycle states

### LOCKED

Canonical states are:

```text
OBSERVED
→ PROPOSED
→ SCREENED
→ EXPERIMENTING
→ EVALUATED
→ APPROVED
→ PROMOTED
→ MONITORED
```

Alternative/terminal states include:

```text
REJECTED
QUARANTINED
ROLLED_BACK
SUPERSEDED
INCONCLUSIVE
```

Exact database labels may differ while preserving these semantics.

## 8. Change classes

### LOCKED

System Evolution changes are classified by what they are allowed to affect.

| Class | Name | Examples | Autonomous production promotion |
|---|---|---|---|
| **SE-0** | Observation / Analysis | detected failure pattern, metric, hypothesis | not a production change |
| **SE-1** | Bounded Behavioral Learning | Agent field note, local strategy hint, reversible non-authoritative preference | may be eligible inside pre-authorized gates |
| **SE-2** | Operational Behavior | Skill revision, workflow strategy, retrieval tuning, prompt/template, qualified model/profile/resource default | only inside explicit pre-authorized policy; otherwise approval |
| **SE-3** | Trusted Product / Security-Relevant Change | trusted code, dependency, broker, storage logic, AuthZ implementation, runtime boundary implementation | **no autonomous production promotion** |
| **SE-4** | Constitutional / Architecture / Governance Change | Constitution, doctrine, MA locks, Owner authority, core security invariants | **never autonomously promoted** |

### LOCKED

The change class is determined by the effective impact, not by the filename or how small the diff appears.

A one-line permission change may be SE-3 or SE-4.

- locked MA-01→MA-20 architecture;
- core doctrine;
- Owner authority;

- AuthZ authority model;
- Capability/Action Assurance invariants;
- secret/root-key architecture;
- cross-Company isolation;
- audit/receipt integrity guarantees;
- supply-chain trust policy;
- release gates.

### LOCKED

Changes to this layer require the Owner/PM architecture-governance path and later deliberate repository persistence.

System Evolution may identify a problem and propose a change; it cannot ratify the change.

## 10. No self-amendment of safeguards

### LOCKED

System Evolution cannot autonomously weaken or remove the controls governing System Evolution itself.

It cannot self-modify, without higher authority:

- promotion thresholds;
- required review;
- protected change classes;
- evaluation holdouts;
- poisoning screens;
- audit requirements;
- AuthZ;
- Action Assurance;
- resource ceilings;
- release gates;
- rollback requirements;
- quarantine rules.

This prevents self-referential privilege escalation.

- runtime errors;
- sanitized observability summaries;
- Brain contradictions;
- Skill Lessons;

### LOCKED

Candidate generation may be automated.

Candidate **promotion authority is separate**.

## 12. Lessons are bounded learning

### LOCKED

A lesson is a candidate behavioral rule derived from evidence.

A lesson may guide future Agent behavior only within its approved scope.

A lesson cannot:

- create permission;
- rewrite architecture;
- change Company ownership;
- change audit policy;
- install trusted code;
- override a revoked human rule;
- become universal merely because it worked once.

### LOCKED

The inherited Skill Lesson gates are retained as a valid example of bounded SE-1 learning.

---

## 13. Evidence requirement

### LOCKED

Every material evolution candidate requires evidence appropriate to its claim.

Evidence may include:

- repeated execution failures;
- human corrections;
- test results;
- benchmark cases;
- security findings;
- regression cases;
- resource measurements;
- comparison artifacts.

### LOCKED

One model's opinion that a candidate is “better” is not sufficient evaluation evidence.

---

## 14. Provenance

### LOCKED

Evolution evidence, candidate datasets, benchmark cases, lessons, and evaluation outputs preserve MA-05 provenance.

The system must be able to determine:

- source;
- capture time;
- Company scope;
- transformation/derivation;
- candidate generation path;
- evaluator;
- model/runtime/tool versions involved.

Provenance must survive summarization and aggregation.

---

## 15. Poisoning threat model

### LOCKED

Potential poisoning/contamination sources include:

- web pages and external research;
- imported documents/files;
- tool output;
- browser content;
- MCP/plugin/Skill content;
- generated code;
- model output;
- Agent memory;
- peer Agent output;
- human/user-provided content;
- compromised artifacts;
- manipulated benchmark cases;
- contaminated observability/log data;
- malicious dependency/update metadata.

### LOCKED

No source becomes trusted because it is repeated, popular, highly ranked, or generated by a trusted-looking model.

---

## 16. Instruction/data separation

### LOCKED

Untrusted evidence is data, not governance instruction.

Content embedded in:

- logs;
- errors;
- web pages;
- documents;
- tool output;
- benchmark cases

cannot instruct the evolution system to:

- alter evaluation rules;
- bypass review;
- install code;
- reveal secrets;
- approve itself;
- change system policy.

This generalizes the safe precedent already present in Ankole Skill Lessons.

---

## 17. Source independence

### LOCKED

Multiple observations copied from one upstream source are not independent corroboration.

Evaluation and confidence logic should preserve source lineage sufficient to distinguish:

- independent evidence;
- duplicated evidence;
- derivative/synthetic evidence.

This follows MA-05.

---

## 18. Quarantine

### LOCKED

Suspicious evolution input or candidate is quarantined when:

- provenance is missing/materially inconsistent;
- malicious instruction contamination is suspected;
- integrity verification fails;
- benchmark contamination is suspected;
- candidate behavior violates hard safety constraints;
- generated executable content is untrusted and awaiting qualification.

### LOCKED

Quarantine is not rejection and not approval.

Quarantined material cannot become the clean baseline for another candidate without explicit validation.

---

## 19. Evaluation environment

### LOCKED

Material candidates are evaluated outside live authoritative production behavior.

Preferred environments include:

- synthetic fixtures;
- recorded/replayed sanitized cases;
- isolated test Company;
- disposable Agent Appliance;
- shadow execution;
- read-only evaluation;
- controlled sandbox.

### LOCKED

Experiments do not mutate live Company authoritative state by default.

Any experiment requiring a real external side effect goes through MA-06 and must be clearly identified as such.

---

## 20. Frozen baseline

### LOCKED

Every comparative evaluation uses a frozen baseline appropriate to the candidate.

The evaluation must identify:

- baseline version/configuration;
- candidate revision;
- dataset/fixture version;
- model/runtime binding;
- tool/Skill versions;
- relevant host/resource profile;
- evaluation contract.

### LOCKED

The baseline cannot silently change during the experiment and still be represented as the same comparison.

---

## 21. Evaluation is multidimensional

### LOCKED

Promotion is not based on one scalar “quality score.”

Evaluation may include:

- correctness;
- task success;
- refusal/safety behavior;
- evidence/provenance quality;
- security;
- privacy;
- reliability;
- resource cost;
- latency;
- determinism/variance;
- usability where relevant;
- compatibility;
- regression risk.

Exact metrics depend on change class.

---

## 22. Hard constraints vs optimization objectives

### LOCKED

Some criteria are **hard gates**, not tradeable objectives.

Examples:

- constitutional security invariants;
- cross-Company isolation;
- secret leakage;
- audit integrity;
- unauthorized external action;
- data corruption;
- permission bypass.

A candidate cannot compensate for a hard safety failure by scoring higher on speed or average task quality.

---

## 23. Goodhart / reward-hacking control

### LOCKED

Evaluation metrics are treated as measurements, not perfect representations of product value.

The architecture must defend against candidates that optimize the metric while degrading actual behavior.

Controls may include:

- multiple independent metrics;
- qualitative review;
- adversarial tests;
- hidden/holdout cases;
- invariant checks;
- post-promotion monitoring.

### LOCKED

A candidate cannot approve itself merely by maximizing the metric used to train/select it.

---

## 24. Evaluation-set separation

### LOCKED

Where practical, evaluation cases used for qualification are separated from the candidate-generation process.

The system should distinguish:

- development/training examples;
- visible regression fixtures;
- holdout qualification cases;
- adversarial cases.

### LOCKED

If a candidate or generating model has access to a holdout set, that set is no longer treated as a clean holdout for the relevant evaluation claim.

---

## 25. Contamination tracking

### LOCKED

Evaluation records must support contamination status such as:

```text
CLEAN
KNOWN_EXPOSED
SUSPECTED
INVALIDATED
```

Exact labels may vary.

A contaminated evaluation may still be informative, but it cannot be represented as an uncontaminated independent qualification.

---

## 26. Self-evaluation

### LOCKED

The same Agent/model that created a candidate may perform preliminary self-checks.

Self-check is useful but is not independent review.

For material SE-2 and all SE-3/SE-4 candidates, required independent evaluation/review cannot be satisfied solely by the candidate generator.

---

## 27. Reviewer independence

### LOCKED

Formal review follows MA-04 independence:

- Reviewer Principal differs from primary candidate executor/generator where formal independence is required;
- materially editing the candidate makes the Reviewer a contributor for that revision;
- another independent review is then required where policy mandates it.

Model diversity may improve evaluation but does not replace Principal/accountability independence.

---

## 28. Human/PM authority

### LOCKED

SE-3 trusted-product changes require the normal engineering/release governance path.

SE-4 architecture/constitutional changes require Owner/PM architecture governance.

System Evolution may prepare:

- evidence;
- candidate;
- test plan;
- comparison;
- recommendation.

It cannot close an architecture gate on its own.

---

## 29. Bounded autonomous promotion

### LOCKED

SerapeumOS may eventually permit autonomous promotion only for explicitly pre-authorized SE-1 and selected SE-2 changes whose envelope is:

- reversible;
- narrow;
- non-security-critical;
- non-constitutional;
- fully evaluated by approved tests;
- provenance-clean;
- within fixed authority/resource limits;
- auditable;
- rollback-capable.

### LOCKED

Autonomous promotion is **deny-by-default** outside such pre-authorized envelopes.

The Agent cannot create or widen the envelope that governs its own promotion.

---

## 30. Promotion

### LOCKED

Promotion is a trusted state transition from evaluated candidate to active approved behavior/configuration.

Promotion must bind to the exact candidate revision that was evaluated.

Changing candidate bytes/configuration after evaluation invalidates the approval/promotion evidence.

---

## 31. Promotion affects new work by default

### LOCKED

A promoted strategy/model/profile/Skill/configuration applies to newly admitted work by default.

Existing in-flight durable executions retain their frozen:

- Task contract;
- model binding where applicable;
- execution attempt;
- approval/action state

unless explicitly re-admitted under the governing policy.

This prevents evolution from mutating work mid-flight.

---

## 32. Canary / staged promotion

### LOCKED

Where appropriate, material changes may be promoted gradually:

```text
isolated evaluation
→ bounded canary
→ monitored expansion
→ default
```

Canary rollout remains Company/local and governed.

### LOCKED

A canary cannot bypass the same hard safety invariants merely because exposure is small.

---

## 33. Monitoring after promotion

### LOCKED

Promotion is not the end of evaluation.

Material promoted changes enter a monitoring period against:

- pre-promotion baseline;
- hard safety invariants;
- failure rates;
- relevant quality/resource metrics;
- new contradiction/security signals.

Post-promotion evidence becomes System Evolution Truth.

---

## 34. Rollback

### LOCKED

Every material promotable candidate should have a defined rollback/supersession path before promotion unless the change is explicitly additive and independently removable.

Rollback:

- restores a previous qualified behavior/configuration where possible;
- preserves candidate/promotion history;
- does not rewrite past execution as if the candidate was never active.

---

## 35. Automatic rollback

### LOCKED

Automatic rollback may be pre-authorized for bounded reversible changes when objective trigger conditions are fixed before promotion.

Examples may include:

- hard invariant failure;
- crash-rate threshold;
- deterministic regression threshold.

### LOCKED

Automatic rollback cannot:

- rewrite architecture/governance;
- bypass audit;
- choose a previously unqualified version;
- expand privilege.

---

## 36. Failure / inconclusive evaluation

### LOCKED

A candidate that fails a hard gate is not promoted.

An inconclusive evaluation is not a pass.

Possible outcomes:

```text
PASS
FAIL
INCONCLUSIVE
QUARANTINE
```

The system must not reinterpret `INCONCLUSIVE` as “probably safe.”

---

## 37. Generated code

### LOCKED

Model/Agent-generated code is untrusted candidate code.

It may not hot-patch trusted production components.

For trusted-product change it must pass the normal path:

```text
candidate code
→ repository diff
→ tests/static/security review
→ independent review
→ MA-19 supply-chain/build controls
→ MA-20 qualification
→ MA-18 controlled update/promotion
```

### LOCKED

Generated code never becomes trusted merely because its tests passed once.

---

## 38. Skills and workflow evolution

### LOCKED

Skill/workflow evolution follows MA-08 and MA-04 boundaries.

A candidate Skill/workflow cannot:

- expand permissions;
- create undeclared network/secrets;
- bypass Action Assurance;
- assign itself higher organizational authority.

Behavioral improvement is allowed only inside existing authority.

---

## 39. Model evolution

### LOCKED

Changing a model/profile/default is MA-07 evolution.

New model bindings must pass:

- profile-specific qualification;
- regression comparison;
- resource compatibility;
- safety/evidence behavior;
- provenance/supply-chain requirements.

System Evolution may recommend/promote only under MA-07/MA-20 policy.

---

## 40. Retrieval/memory evolution

### LOCKED

Changes to:

- retrieval;
- ranking;
- memory consolidation;
- epistemic confidence;
- contradiction processing

must preserve MA-05 invariants.

No optimization may convert retrieval score into truth authority or remove provenance requirements.

---

## 41. Resource-policy evolution

### LOCKED

System Evolution may suggest improved MA-11 quotas/scheduling.

It cannot autonomously increase its own resource ceiling or disable the trusted Host Safety Reserve.

Pre-authorized bounded tuning may only operate inside Owner-defined upper/lower limits.

---

## 42. Reliability-policy evolution

### LOCKED

System Evolution may propose:

- retry changes;
- checkpoint cadence;
- failure classification;
- recovery improvements.

It cannot autonomously:

- remove fencing;
- create unbounded retries;
- treat unknown external outcomes as success;
- disable reconciliation requirements.

MA-12 invariants remain hard gates.

---

## 43. Security evolution

### LOCKED

Security-sensitive improvements may be discovered/proposed automatically.

Their production promotion is SE-3 or SE-4 and therefore not autonomous.

This includes changes to:

- sandbox/isolation;
- runtime credentials;
- AuthZ;
- capability issuance;
- Action Assurance;
- secret handling;
- audit integrity;
- supply-chain verification.

---

## 44. Privacy and telemetry use

### LOCKED

Observability data does not automatically become an evolution dataset.

MA-14 privacy/retention policy determines whether sanitized telemetry may be used for evaluation/learning.

### LOCKED

System Evolution should prefer:

- aggregated metrics;
- minimal necessary event metadata;
- explicit failure evidence;
- curated fixtures

over bulk ingestion of private raw prompts/logs.

---

## 45. Cross-Company learning

### LOCKED

Private data, lessons, failures, prompts, Tasks, or artifacts from Company A do not automatically train/evolve Company B behavior.

Company-scoped evolution remains isolated by default.

### LOCKED

A future installation-global learning corpus requires a separately governed policy that preserves:

- source consent/authority;
- provenance;
- privacy;
- de-identification where appropriate;
- Company isolation;
- reversibility.

There is no implicit cross-Company learning pool.

---

## 46. External training / data export

### LOCKED

SerapeumOS does not export Owner/Company data for external model training, evaluation, analytics, or improvement by default.

Any external data export is a governed MA-06/MA-08 publication/action.

Final core System Evolution must function locally.

## 47. Fine-tuning / training

### LOCKED

System Evolution is **not synonymous with model training**.

It may evolve:

- lessons;
- Skills;
- workflows;
- prompts;
- model selection;
- retrieval;
- configuration;

Local fine-tuning/training may be added later as an optional qualified mechanism.

## 48. NaraRouter boundary

### LOCKED

NaraRouter may temporarily provide inference during development/evaluation under the Owner's existing exception.

It is not:

- the evolution authority;
- a training datastore;
- a mandatory evaluator;
- a required promotion service;
- a final production dependency.

All evolution records/evidence remain local under SerapeumOS control.

## 49. Evaluation models are not judges of authority

### LOCKED

A model may act as an evaluator, critic, grader, or adversarial tester.

Its output is evaluation evidence.

It does not itself authorize production promotion.

Where model-based grading is used:

- grader identity/version is recorded;
- calibration/regression is evaluated;
- deterministic/hard checks remain separate where possible.

---

## 50. Benchmark ownership

### LOCKED

SerapeumOS maintains versioned evaluation suites appropriate to each change class/profile.

Suites may contain:

- regression fixtures;
- adversarial fixtures;
- invariant tests;
- performance/resource cases;
- reliability/failure-injection cases;
- privacy/security cases.

Detailed release suite composition belongs to MA-20.

---

## 51. Test fixture provenance

### LOCKED

Evaluation fixtures themselves have provenance and version identity.

A silently edited fixture invalidates direct comparison to earlier scores unless the change is explicitly versioned.

Benchmark evolution is itself System Evolution Truth.

---

## 52. Benchmark gaming

### LOCKED

Production promotion cannot depend exclusively on tests whose exact answers/cases were available to the candidate-generation process where gaming is material.

Where strong holdouts are impractical, the evaluation must disclose that limitation rather than overstate confidence.

---

## 53. Negative evidence

### LOCKED

Failed experiments, rejected candidates, reverted promotions, and security findings remain useful evolution history.

They must not be discarded merely because the candidate was not promoted.

This prevents rediscovery/reintroduction of known bad changes.

---

## 54. Revoked rules / rejected candidates

### LOCKED

Explicit human revocation or rejected safety rule must remain visible to future candidate-generation processes where relevant.

A future candidate that effectively reintroduces a revoked behavior must be recognized as such rather than bypassing the revocation through rewording.

This extends the useful inherited Skill Lesson rule that revoked content remains banned.

---

## 55. No silent recurrence

### LOCKED

Candidate deduplication/similarity mechanisms should identify:

- duplicate rejected candidates;
- previously rolled-back behavior;
- revoked lessons;
- known poisoning patterns.

Similarity is an alerting aid, not truth authority.

---

## 56. Evolution resource governance

### LOCKED

System Evolution workloads are MA-11 **P3 BACKGROUND / LEARNING / EVOLUTION** by default.

They are:

- budgeted;
- bounded;
- preemptible;
- lower priority than Owner control and committed Company work.

### LOCKED

A self-improvement process cannot starve the Company in order to improve the Company.

---

## 57. Evolution scheduling

### LOCKED

Evolution may run:

- periodically;
- after sufficient evidence accumulates;
- after failures/incidents;
- by explicit Owner request;
- as part of release qualification.

The trigger does not change promotion authority.

---

## 58. Audit

### LOCKED

Material evolution transitions are auditable under MA-14.

Audit includes, as applicable:

- candidate creation;
- source/proposer;
- quarantine;
- evaluation start/result;
- Reviewer decision;
- Owner/authorized approval;
- promotion;
- automatic/manual rollback;
- supersession;

---

## 59. Receipts

### LOCKED

Promotion and rollback of consequential configuration/system behavior produce durable receipts appropriate to their change class.

A model saying “candidate promoted” is not sufficient evidence.

---

## 60. Disaster recovery

### LOCKED

System Evolution Truth, active promoted-version references, and necessary evaluation/promotion history are part of recoverable authoritative state under MA-13.

After restore:

- active evolution policy/version state is reconstructed from trusted data;
- runtime experiments are not blindly resumed;
- in-flight promotion actions are reconciled.

---

## 61. Supply-chain interaction

### LOCKED

Any candidate introducing executable code, dependency, model artifact, extension, runtime, or binary must satisfy MA-19 provenance/supply-chain rules before trusted promotion.

A high evaluation score cannot override an untrusted/unknown software supply chain.

---

## 62. Update interaction

### LOCKED

Trusted product-code evolution is deployed only through MA-18 controlled installation/update/migration/rollback mechanisms.

System Evolution does not maintain a secret alternate hot-update channel.

---

## 63. Release interaction

### LOCKED

MA-20 defines the executable qualification gates that prove a candidate/change class satisfies required:

- functionality;
- security;
- privacy;
- reliability;
- resource;
- recovery;
- regression

criteria.

An MA-15 `EVALUATED` candidate is not necessarily release-qualified.

---

## 64. Evolution safety invariant

### LOCKED

The central invariant is:

> **The part of the system being improved cannot be the sole authority deciding that its own improvement is safe to promote.**

This is enforced through:

- trusted promotion services;
- fixed hard invariants;
- independent review where required;
- Owner/PM authority for protected classes;
- versioned evidence;
- audit/receipts;
- rollback.

---

## 65. Failure behavior

### LOCKED

If evolution infrastructure fails:

- production remains on the last qualified/promoted state;
- candidate generation may pause;
- candidate evaluation may become inconclusive;
- no unvalidated candidate is promoted;
- incomplete experiments remain isolated;
- no safety requirement is weakened to “keep evolution working.”

System Evolution is not required for core Company continuity.

---

## 66. Veto conditions

An MA-15 implementation is invalid if it:

- lets an Agent/model directly rewrite locked architecture or governance;
- lets candidate-generated instructions change evaluation/promotion rules;
- treats telemetry/logs as an automatic training corpus;
- promotes based only on the candidate generator's self-evaluation;
- uses a single scalar score to trade away hard security/privacy invariants;
- treats repeated poisoned data as corroborated truth;
- lets quarantined data silently become a clean baseline;
- leaks one Company's private evolution data into another Company by default;
- exports Owner data externally for training/evaluation without governed authorization;
- lets generated code hot-patch trusted production;
- lets System Evolution weaken its own safeguards or resource ceilings;
- silently modifies in-flight frozen executions after promotion;
- automatically promotes SE-3 trusted-code/security changes;
- autonomously promotes SE-4 constitutional/architecture changes;
- treats `INCONCLUSIVE` as pass;
- hides failed/rolled-back candidates;
- introduces mandatory NaraRouter/cloud dependency;
- creates an unaudited alternate update/promotion channel.

---

## 67. MA-15 closure decision

### CLOSED

MA-15 is architecture-complete.

Locked:

- System Evolution Truth as a separate durable domain;
- observe → evaluate → propose → screen → experiment → compare → review → approve → promote → monitor → rollback lifecycle;
- immutable/versioned candidate identity;
- explicit SE-0→SE-4 change classes;
- protected architecture/governance layer;
- no self-amendment of evolution safeguards;
- bounded learning from Ankole Dreaming/Skill Lessons;
- mandatory provenance;
- poisoning/contamination threat model;
- instruction/data separation;
- quarantine;
- isolated experimentation;
- frozen baselines;
- multidimensional evaluation with hard gates;
- anti-Goodhart/holdout/contamination controls;
- independent review;
- bounded pre-authorized autonomy for only eligible SE-1/SE-2 classes;
- no autonomous SE-3/SE-4 production promotion;
- staged promotion and post-promotion monitoring;
- rollback/supersession;
- generated code remains untrusted;
- Company-scoped/private learning;

## 68. Decisions to persist

When repository persistence is available, record decisions equivalent to:

### D-151 — System Evolution Truth is a separate durable domain
Candidates, evaluations, approvals, promotions, rollbacks, and evolution history do not overwrite Organizational, Execution, or Epistemic Truth.

### D-152 — Evolution uses candidate → evaluation → governed promotion
Learning/model output/generated code may create candidates but cannot directly modify trusted production behavior.

### D-153 — Evolution changes are classified SE-0 through SE-4
Only explicitly pre-authorized bounded SE-1 and selected SE-2 changes may ever qualify for autonomous production promotion; SE-3 and SE-4 cannot.

### D-154 — Architecture and constitutional safeguards are protected from autonomous evolution
Owner authority, MA locks, TCB, AuthZ, Action Assurance, secrets, audit, Company isolation, and release/supply-chain governance require higher-authority change paths.

### D-155 — Evolution cannot amend its own safeguards
Promotion gates, evaluation policy, poisoning screens, audit, authority, resource ceilings, and protected change classes cannot be autonomously weakened by the system they govern.

### D-156 — Evolution evidence requires provenance and contamination status
Training/evaluation examples, lessons, telemetry-derived signals, and candidate evidence retain source lineage and contamination/holdout status.

### D-157 — Material candidates are tested against frozen baselines in isolation
Live authoritative state is not the default experiment environment; candidate/baseline/dataset/model/tool versions are fixed and recorded.

### D-158 — Hard safety invariants cannot be traded for aggregate quality
Security, privacy, authority, isolation, and corruption failures are release blockers regardless of average benchmark improvement.

### D-159 — Independent review separates candidate creation from material approval
Self-evaluation is supplementary evidence; material SE-2 and all SE-3/SE-4 changes require the independent/higher-authority review path defined by policy.

### D-160 — Poisoned or suspicious evolution inputs are quarantined
External content, logs, model/tool output, generated code, Skills/plugins, and contaminated benchmarks remain untrusted until screened/qualified.

### D-161 — Promotion changes new work by default
Existing frozen durable executions are not silently mutated by newly promoted models, Skills, strategies, or configuration.

### D-162 — Promotion is reversible and monitored
Material promoted behavior has rollback/supersession policy and post-promotion monitoring; failed candidates/history are preserved.

### D-163 — Generated trusted-product code never self-deploys
Generated code follows repository review, MA-19 supply-chain/build controls, MA-20 qualification, and MA-18 controlled update/promotion.

### D-164 — Company learning is isolated by default
Private Company data/lessons/telemetry do not become cross-Company/global evolution data without separately governed policy.

### D-165 — Final System Evolution is local and cloud-independent
No external training, hosted evaluator, NaraRouter, or cloud improvement service is required for final SerapeumOS evolution.
